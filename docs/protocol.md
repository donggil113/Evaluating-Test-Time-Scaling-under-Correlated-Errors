# Protocol N5-v1 (frozen before any test-split evaluation)

Status of this document: written and committed **before** any policy was run on
test problems. Changes after that commit must be listed in `STATUS.md` as
deviations.

## 1. Question

When a generator's candidates are checked by an imperfect LLM verifier whose
repeated verdicts are correlated, what is the marginal value of one more
verifier call compared with one more generation, once every generator,
verifier and controller cost is counted? Can a calibrated stopping rule turn
that value into a better cost–error trade-off than fixed allocations?

## 2. Data (real traces only)

| item | value |
|---|---|
| source | Singhi et al. 2025, *When To Solve, When To Verify*, HF org `sc-genrm-scaling` |
| files | `GPQA_diamond_Solutions_Llama-3.3-70B-Instruct` (sha256 af885f39…), `GPQA_verifications_GenRM-Base_Llama-3.3-70B-Instruct` (sha256 fea30c7e…) |
| problems | 64 GPQA-Diamond questions (the authors' random subset) |
| generator | Llama-3.3-70B-Instruct, T=0.7, 256 candidates / problem |
| verifier | Llama-3.3-70B-Instruct as GenRM-Base (self-verification), T=0.7 |
| verified pool | candidates 0–63 of each problem, 32 verifier calls each |
| gold | released `gt_answer` letter (dataset answer key; never generated by us). The original GPQA file is gated, so it was not re-checked against the source. |
| table | 64 × 256 candidates, 64 × 64 × 1 × 32 = 131,072 verifier calls |

Parsing depends on output text only. Candidate answers that cannot be parsed
(487, all truncated at ≥1024 tokens) are abstentions and count as wrong if
returned. Unparseable verdicts (8) carry no evidence but are charged.

## 3. Split and seeds

* 32 dev / 32 test problems, by salted SHA-256 of the question text
  (`scripts/build_table.py`, salt `ttsce-split-v1|`). Fixed before any outcome
  was inspected.
* Everything that is fit or selected (Beta/Beta-binomial parameters, posterior
  weights, stopping thresholds, schedule, aggregator, N, V) uses dev only.
* Order seeds 0–19: each seed fixes the candidate order and the per-candidate
  verifier-repeat order. Per-problem error = mean over the 20 seeds.

## 4. Scope of the runner

* Fixed candidate pool; history-independent queries: each policy executes a
  query schedule fixed in advance and may only decide to stop
  (`src/ttsce/env.py`). With this restriction, replaying pre-collected i.i.d.
  responses is exactly equivalent to live querying.
* Policies see only the revealed answers/verdicts (`Observation`). Gold and
  unrevealed cells are unreachable; checked by a mutation test and a negative
  control (`tests/test_replay.py`).
* Out of scope (NOT_RUN, needs a live online runner): history-dependent query
  selection (e.g., choosing which candidate to verify from past verdicts),
  multi-turn verification.
* Model-diversified verifiers: the released GPQA pool has one verifier only,
  so a head-to-head "repeat vs diversified verifier" on the same pool is
  NOT_RUN here (data exists for MATH-128 with two fine-tuned verifiers, but it
  needs ~1 GB of new downloads; see STATUS.md).

## 5. Policies

Fixed allocations `FIX(N, V)` — N generations, V verifier calls per candidate:
* `MV` majority vote (N up to 256, V = 0)
* `BoN` best-of-N by mean acceptance (Singhi et al.'s GenRM selection)
* `WMV` acceptance-weighted majority vote
* `BAYES-IND`, `BAYES-CORR` argmax of the calibrated answer posterior (below)

grids: N ∈ {1,2,4,8,16,32,64}, V ∈ {1,2,4,8,16,32}; MV also N ∈ {128,256}.

Stopping policies (fixed schedule + stop rule):
* `AC`: Adaptive-Consistency Beta criterion (Aggarwal et al. 2023) on the
  generate-only schedule `G` (max 256), threshold c ∈ {0.5,…,0.999}.
* `STOP-{IND,CORR}-G`: calibrated posterior on `G`.
* `STOP-{IND,CORR}-GVk`: schedule "generate one candidate, verify it k times"
  for k ∈ {1,2,4,8}, max 64 candidates.
  Stop when max posterior ≥ τ, τ ∈ {0.5,…,0.999}.

Answer posterior (`src/ttsce/models.py`): vote term from a Beta prior over
per-problem candidate accuracy; verdict term per candidate is either
independent Bernoulli (IND, the Odds-Law assumption) or Beta-binomial
(CORR, the exchangeable partially-correlated-gate model). Two scalar weights
(vote, verdict) are fit on dev states by log-loss (temperature calibration).

## 6. Costs

* Primary: total tokens (prompt + completion) of all generator and verifier
  calls, no caching. Generator and verifier are the same 70B model, so FLOPs
  ≈ 2 · 70e9 · tokens for both.
* Secondary: completion tokens only; prompt-prefix-cached tokens.
* Controller: CPU seconds of the policy's own computation, reported separately.
* Full table collection cost (what the original authors paid for all 256
  generations and 131k verifier calls) is reported separately from the cost
  of executing each policy.

## 7. Selection and endpoints

Budgets B ∈ {2,4,8,16,32,64,128,256} × c̄_gen, c̄_gen = dev mean total tokens
of one generation call. For each B, on dev, pick the lowest-dev-error policy
with dev mean cost ≤ B within each family:
`GEN` (MV, AC, STOP-*-G), `VER` (all policies that call the verifier),
`FIXED` (all FIX incl. MV), `STOP` (AC and all STOP-*), `STOP-IND`, `STOP-CORR`.

Test endpoints per budget (32 test problems, paired):
* E1 verification value: err(VER) − err(GEN)
* E2 stopping value: err(STOP) − err(FIXED)
* E3 correlation awareness: err(STOP-CORR) − err(STOP-IND); plus log-loss and
  ECE of IND vs CORR posteriors on test states
* the realised test mean cost of every selected policy

Statistics: problem-level paired bootstrap (10,000 resamples of test
problems); 95% percentile CIs; Holm adjustment across the 8 budgets within
each of E1, E2. Verifier repeats are never counted as independent samples.

Measurement endpoints (descriptive, all 64 problems, problem-cluster
bootstrap), dev and test reported separately:
* M1 within-candidate correlation of repeated verdicts (Beta-binomial ρ) for
  correct and wrong candidates; blind-spot mass (wrong candidates accepted in
  all 32 calls).
* M2 PCVC moment test: fit Beta on 8 repeats, predict the all-accept rate of
  k = 1…24 further gates on the held-out 24 repeats; compare with the
  independence prediction.
* M3 where the correlation lives: share of variance in false-accept
  propensity explained by problem, by (problem, answer) and within answer.

## 8. Decision rule

* **NO_GO** if the only supported findings restate known results: correlated
  repeats / diminishing gates (PCVC, Odds Law), self-consistency ≥ GenRM at
  matched compute (Singhi et al.), false-positive ceilings (Stroebl et al.);
  or if any oracle leak is found.
* **GO** if (a) a STOP policy beats the best FIXED policy (E2) or CORR beats
  IND (E3) on test at ≥ 1 budget with Holm-adjusted CI excluding 0 and is not
  significantly worse at any budget, with controller overhead included; or
  (b) a measurement (M1–M3) yields a practical evaluation conclusion that is
  not implied by the prior work above and replicates on the test split.
* **PIVOT** if effects appear on dev but test CIs include 0, or the question
  can only be settled with verifier diversity / more generator–verifier pairs
  than the approved data provide.
* **BLOCKED_REALDATA** if no real trace is usable.
